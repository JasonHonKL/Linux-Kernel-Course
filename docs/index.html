    内核 C 的五个习惯

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    先看一个最常见的动作：你手里只有 struct kc_item 里的 node 指针，怎么拿到外层结构？内核不额外存 back-pointer，而是用偏移量反推。

    include/linux/container_of.h:19
    #define container_of(ptr, type, member) ({				\
	static_assert(__same_type(*(ptr), typeof_member(type, member)) || \
		      __same_type(*(ptr), void),			\
		      "pointer type mismatch in container_of()");	\
	(type *)((void *)(ptr) - offsetof(type, member)); })

    第二个习惯是侵入式链表：链表节点嵌在业务结构里，不单独分配。遍历时用 container_of 从节点反推对象。

    • ERR_PTR：指针返回值用负错误码编码，调用方用 IS_ERR / PTR_ERR 判断，避免额外的 out 参数。

    地址空间：__user、__iomem、DMA

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    “地址”在内核里不是一个概念，而是四个：用户虚拟地址、内核虚拟地址、设备 MMIO 地址、DMA 总线地址。它们的解引用方式完全不同。

    include/linux/compiler_types.h:50
    # define __user		__attribute__((noderef, address_space(__user)))
# define __iomem	__attribute__((noderef, address_space(__iomem)))

    __user 不是运行时检查，而是 sparse 的标记：它让“直接解引用用户指针”在静态分析里报警。运行时仍然要靠 access_ok 与 copy_*_user。

    预测驱动拿到一个 void __iomem *base，读寄存器应该用：

    为什么不能直接解引用用户指针

    用户地址可能未映射、可能被换出、可能属于另一个进程。直接读会触发 kernel oops，而不是返回 -EFAULT。正确路径是让 uaccess 在异常表保护下访问。

    include/linux/uaccess.h · __copy_from_user
    static __always_inline __must_check unsigned long
__copy_from_user(void *to, const void __user *from, unsigned long n)
{
	unsigned long res;

	might_fault();
	instrument_copy_from_user_before(to, from, n);
	if (should_fail_usercopy())
		return n;
	check_object_size(to, n, false);
	res = raw_copy_from_user(to, from, n);
	instrument_copy_from_user_after(to, from, n, res);
	return res;
}
    DMA 的地址

    设备看到的地址不一定是 CPU 物理地址：dma_map_single() 返回 dma_addr_t，要由 IOMMU 或平台翻译。CPU 用内核虚拟地址，设备用 DMA 地址，两者不能混。

    四个对象

    sk_buff 与 net_device

    sk_buff 不是“一块内存”，而是“一块内存 + 四个指针 + 元数据”。同样一块 buffer，协议层可以不断 push/pull 头部，而不复制数据。

	union {

			struct sk_buff		*next;
			struct sk_buff		*prev;

				struct net_device	*dev;

			};

		struct rb_node		rbnode;
		struct list_head	list;
		struct llist_node	ll_node;

	struct sock		*sk;

    地址：sockaddr、IP、CIDR、MAC

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    网络里的“地址”至少有三层：sockaddr（API 表示）、IP 地址（网络层）、MAC 地址（链路层）。它们的字节序、长度和含义都不同。

    include/uapi/linux/in.h:260 · sockaddr_in
    struct sockaddr_in {
  __kernel_sa_family_t	sin_family;	/* Address family */

  struct in_addr	sin_addr;	/* Internet address */
  unsigned char		__pad[__SOCK_SIZE__ - ...];
};

    sin_port 和 sin_addr 都是网络字节序；sin_family 是本机字节序。混用是网络代码最常见的 bug 之一。

    CIDR 与最长前缀

    路由表不按“完整 IP”匹配，而按前缀长度匹配：10.1.2.0/24 比 10.0.0.0/8 更具体。查找时取最长匹配，这就是 FIB 的核心。

    MAC 地址则是 6 字节链路层标识，由 ARP/ND 从 IP 解析出来。IP 是端到端的逻辑地址，MAC 是逐跳的物理地址。

    内核里的地址类型

    __be32 表示“大端 32 位”，__be16 表示大端 16 位；u32 是本机字节序。读网络代码时，先看类型，再决定是否需要 ntohl/htonl。

    sk_buff 是网络栈的“通用货币”。同一块内存，TCP 加头、IP 加头、驱动加 DMA 映射，靠的都是 head/data/tail/end 四个指针。

    模块 5 · 小节 1

    sk_buff 的四个指针

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    不要把 sk_buff 想成“一个包的内存”。它描述的是一块 buffer 上的一个窗口：head 是分配起点，data/tail 是当前有效数据，end 是终点。

    include/linux/skbuff.h:2933 · skb_reserve
    static inline void skb_reserve(struct sk_buff *skb, int len)
{
	skb->data += len;
	skb->tail += len;
}

    skb_reserve 同时移动 data 与 tail，预留头部空间；之后 skb_push 只需把 data 往前挪，不搬运数据。

    预测给一个 skb 预留 16 字节 headroom，然后 push 14 字节以太网头。data 相对 head 的位置是？

    常用操作

    • skb_put：在尾部追加数据，返回旧 tail。
    • skb_push：在头部插入，返回新 data。
    • skb_pull：从头部移除（消费），返回旧 data。
    • skb_trim：缩短尾部。

    这些函数都只移动指针并做边界检查；真正昂贵的拷贝发生在 skb_copy、跨 namespace 或用户态拷贝。理解这一点，才能解释“零拷贝”到底省了什么。

    skb 的所有权

    skb 可以用引用计数共享（skb_get），也可以 clone（共享数据、独立元数据）。释放用 kfree_skb；谁分配谁负责，转发路径要特别小心。

    TCP 发送与 qdisc

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    tcp_sendmsg 不是“把数据直接交给网卡”。它把用户数据拷贝进 skb、维护发送队列与序列号，再由 tcp_transmit_skb 加 TCP/IP 头，最后交给 qdisc。

    锁与队列

    tcp_sendmsg 先 lock_sock，再调用 tcp_sendmsg_locked。这把锁保护的是 socket 的发送状态；同一个 socket 的并发发送会被串行化。

    net/ipv4/tcp.c:1449 · tcp_sendmsg
    int tcp_sendmsg(struct sock *sk, struct msghdr *msg, size_t size)
{
	int ret;

	lock_sock(sk);
	ret = tcp_sendmsg_locked(sk, msg, size);
	release_sock(sk);

	return ret;
}

    每个 skb 进入 sk_write_queue，直到被 ACK 确认才释放。qdisc 位于 IP 层之下，决定“现在发、稍后发、丢哪个”。这就是为什么 sendto 成功不等于网卡已发。

    地址与下一跳

    TCP 不知道 MAC；它只填 IP 地址。路由与邻居在 IP 层完成，qdisc 只看到已经封装好的 skb 和出口设备。

    NAPI 的取舍

    每个包一次中断会在高 PPS 下把 CPU 打满。NAPI 的做法是：第一个包触发中断，随后关闭该队列中断，改用 napi_poll 批量收包，直到预算用完或队列空，再重新开中断。

    net/core/dev.c:7991 · napi_poll
    static int napi_poll(struct napi_struct *n, struct list_head *repoll)
{
	bool do_repoll = false;
	void *have;
	int work;

	list_del_init(&n->poll_list);
	have = netpoll_poll_lock(n);

	work = n->poll(n, n->weight);

	if (work >= n->weight) {
		do_repoll = true;
		...
	}
	...
}

    “预算/权重”决定一次轮询最多处理多少包，避免一个队列长期霸占 CPU。多队列网卡会把不同 flow 散列到不同队列，再分别绑定 CPU。

    模块 6 · 小节 2

    XDP 与 eBPF

    阅读 ≈7 分钟 · 检查 ≈5 分钟

    XDP 是网卡驱动收包路径上的一个钩子：在分配 skb 之前，直接对 xdp_buff 做判断，可以 XDP_DROP、XDP_PASS、XDP_TX 或重定向。它比 netfilter 更早、更快。

    安全边界：verifier

    eBPF 程序不是普通内核模块：它不能任意跳转、不能越界访问、不能无限循环。加载前 verifier 会做控制流与内存安全检查，确保程序不会把内核打崩。

    kernel/bpf/verifier.c:23783 · bpf_check
    int bpf_check(struct bpf_prog **prog, union bpf_attr *attr,
	      bpfptr_t uattr, u32 uattr_size)
{
	...
	ret = bpf_check_attach_target(...);
	...
	ret = do_check_main(...);
	...
}

    XDP 程序的典型结构是：读 Ethernet → 检查边界 → 读 IP → 判断 protocol → 返回动作。每一次访问都要先证明“没有越界”，否则 verifier 拒绝加载。

    性能与可观测性

    XDP 适合 DDoS 过滤、负载均衡、采样；但调试比普通代码难。先用 bpftool prog load / ip link set xdp 验证，再用 map 计数，别一上来就写复杂逻辑。

    用自己的话解释

    ≈3 分钟 · 本地保存
    0 字
    参考答案

    XDP 在驱动收包路径上、分配 skb 之前运行，直接操作 xdp_buff，所以省掉了 skb 分配、协议栈解析等固定成本，适合线速过滤与重定向。verifier 在加载前做静态检查，证明程序不会越界、不会无限循环、不会破坏内核状态，否则任意 eBPF 程序就等于任意内核代码。两者不矛盾：XDP 把执行点提前以获得性能，verifier 把“可执行范围”限制在可证明安全的子集里。

    本小节可以带走

    • XDP 在 skb 之前处理，动作有 DROP/PASS/TX/REDIRECT。
    • eBPF 程序必须通过 verifier 的内存与控制流检查。
    • 越早的钩子性能越好，但可用的内核功能越少。
